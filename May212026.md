# PropEase - Project Progress Summary (May 21, 2026)

This document provides a comprehensive summary of recent features, optimizations, and constraints implemented in **PropEase**, specifically focusing on robust user authentication/verification and the interactive Maintenance Kanban system.

## 1. Authentication, Verification & Profile Creation

To clean up legacy profiles and secure the system, a proper authentication gate was implemented. 

### Key Constraints & Rules
- **Gmail Restriction**: Signups are strictly limited to `@gmail.com` email addresses. Non-Gmail signup attempts return a validation error.
- **Pre-Verification Requirement**: A profile is *only* created in the database after the user's email has been verified via a one-time passcode (OTP).

### Implementation Architecture
```
[Sign-Up UI Form] ──(Validates @gmail.com)──> [requestSignUpOtpFn]
                                                    │
                                           (Generates 6-Digit OTP)
                                           (Saves data to verification_codes)
                                           (Prints OTP to dev server console)
                                                    │
[OTP Verification Screen] <──(Checks Console)─── [Developer/User]
        │
   (Submits Code)
        │
        └──> [verifyOtpAndSignUpFn] ──(Bypasses with "000000" in Dev)──> [Create Profile & Establish Session]
```

1. **OTP Request & Temporary Storage (`requestSignUpOtpFn`)**:
   - Generates a random 6-digit verification code.
   - Hashes the password and serializes the registration data (first name, last name, password hash, role, and any invite tokens) into a temporary JSON payload.
   - Saves this record inside a new `verification_codes` schema table in SQLite, set to expire in 15 minutes.
   - **Local Delivery**: Prints a clearly demarcated verification card to the npm development server CLI console.
2. **OTP Verification & Account Provisioning (`verifyOtpAndSignUpFn`)**:
   - The user inputs the code on the screen.
   - In local development (`DEV` mode), a universal bypass code of `"000000"` is supported to ease automated testing.
   - Once verified, the database record is cleared, the profile is formally created, and any incoming property invitation tokens are accepted (updating leases, establishing primary tenant links, generating initial invoices, and marking the unit as `"occupied"`).
   - Generates a JWT session token and sets it as an HTTP-only, secure cookie (`propease_session`).

## 2. Interactive Maintenance Kanban Board

A central Kanban board was developed for property owners, landlords, and managers to coordinate maintenance requests.

### Key Enhancements & Business Rules

### A. Restricted Worker Assignment
- **Query Filter**: Modified [queries.ts](file:///d:/Projects/Active/Cool-Projects/PropEase/src/db/queries.ts#L332) to filter out landlords and managers.
- **Result**: Landlords and managers can only assign requests to users containing the role `"maintenance"` or `"service"`, eliminating user assignment errors.

### B. Forbidden Status Regression (No Drag-Back-To-Open)
- Once a maintenance request transitions to `"in_progress"` or `"resolved"`, it cannot be returned to `"pending"` (Open).
- **Drag Constraint**: The drag-over hover styling is disabled on the "Open" column if the card being dragged is already active or resolved.
- **Drop Constraint**: Drop attempts targeting the "Open" column are rejected on the client side, triggering a visual error toast.
- **Details Modal Constraint**: In the request slide-out detail dialog, the "Open" status selector dropdown option is disabled if the ticket is already in progress or resolved.

### C. Global Unit Status Propagation
- Database queries use an atomic database transaction in `updateMaintenanceRequest()` to synchronize statuses globally across the application.
- **Status Rules**:
  - **In Progress**: When a maintenance request status changes to `"in_progress"`, the associated unit's status is automatically set to `"maintenance"`.
  - **Resolved**: When a request status updates to `"resolved"`, the system queries for an active lease on that unit. If an active lease exists, the unit reverts to `"occupied"`; otherwise, it reverts to `"vacant"`.
- **Global Views**: This status change immediately propagates to dashboards, property tables, and maps, rendering yellow maintenance status badges.
